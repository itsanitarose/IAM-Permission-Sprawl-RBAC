
# 03. Segregation of Duties (SoD)

This document examines the risks created by conflicting permissions in the Billing system. It identifies where segregation of duties (SoD) controls are needed to prevent one person from completing sensitive financial transactions without independent oversight.

<br>

## 1. Conflicting Access Matrix

The table below identifies potentially dangerous permission combinations and the controls I recommend.

| Conflicting Permissions | What Could Go Wrong | Recommended Control |
|---|---|---|
| Create new payee + Approve payments | Someone could create a fake supplier using bank details they control, then approve payments for work that was never done. | **Separation of duties:** Prevent users from approving payments to payees they created without independent approval. |
| Edit patient billing details + Approve payments | If the application allows changes to payment amounts or recipient details, someone could manipulate those details and approve the transaction themselves. | **Independent approval:** Require another authorised person to review sensitive billing changes before the related payment is approved. |
| System Admin + Financial permissions | Someone could misuse financial access while also controlling administrative settings. If administrators can change audit settings or logs, they might also interfere with the detection of misuse. | **Role separation:** Keep financial permissions separate from routine system administration. Use time-limited just-in-time (JIT) access for approved administrative tasks and protect audit records from alteration. |

These combinations require further validation against the application's actual capabilities. The permission records identify potential conflicts but do not confirm that every scenario is possible.

<br>

## 2. The Billing Supervisor Exception

Billing Supervisors are expected to create invoices and approve refunds. Removing either permission would conflict with the supplied job requirements.

However, this creates a potential conflict: **a supervisor could create an invoice and approve a refund against it**, if the application allows that workflow.

The recommended approach is to retain legitimate responsibilities while introducing checks against self-approval and improper refunds.

<br>


### Recommended Controls

- **Self-approval restriction:** Prevent supervisors from approving refunds against invoices they created, where the application supports this control.

- **Payment verification:** Require refunds to be linked to verified original payments and returned to the original payment method, with separately approved exceptions.

- **Approval thresholds:** Require independent manager approval for refunds above an agreed financial limit.

- **Unusual activity monitoring:** Flag repeated refunds, unusual recipients and refunds that cannot be matched to verified payments.

These controls would need to be confirmed with the Billing team and tested against the application's refund process before implementation.


<br>

## 3. My Assessment

The concern is not simply that employees hold too many permissions. It is whether those permissions allow someone to **create a financial transaction, approve it and potentially benefit from it without independent oversight**.

My recommendations focus on separating conflicting responsibilities, introducing independent approvals and replacing unnecessary standing administrative access with JIT access where appropriate.

The aim is to reduce opportunities for financial misuse while allowing employees to carry out their legitimate responsibilities.

**Limitations:** These are potential misuse scenarios based on the supplied access records. They are not evidence that fraud occurred or confirmation that every described action is possible in the application.
